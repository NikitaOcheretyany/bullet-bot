# Локальные дополнения к bullet-bots

Основа — `bulletxyz/bullet-bots`, commit
`cb7c011c70a01f21e64f46fade34d89545335ada`.

## Торговая часть

В существующей `reference-arb` реализованы условия lead–lag для одной пары:
Binance USDⓈ-M `LITUSDT` → Bullet `LIT-USD`. Подключения, ключ, harness,
брокер, учёт позиции и выдача client ID остаются штатными.

Параметры находятся в `config/reference-arb-example.toml`: EMA basis 300 с,
порог A строго > 2 bp от ask/bid Bullet, импульс за 250 мс строго > 1 bp,
резерв B = 1 bp от fair на момент сигнала. Это пример B, а не подобранное значение.
Выход: remaining ≤ R = −1,5 bp / PnL ≤ −5 bp / время 60 с.
Текущий размер — до 100 USD по цене расчёта заявки; количество округляется вниз
по LOT_SIZE из уже загруженных фильтров брокера. Для LIT шаг 1 LIT;
лимит IOC = fair_signal × exp(−sB/10000), покупку округляем вниз, продажу вверх.
Повтор стороны — после сброса edge до A или ниже либо 10 с от закрытия/пустого IOC.
Частичный вход принимается без добора, выход закрывает фактическую позицию.

`exit = { mode = "fair", remaining_bps = -1.5 }` выбирает выход по fair.
Альтернатива — `exit = { mode = "trailing", drawdown_bps = 2.0 }`:
откат от лучшего bid для long / ask для short после первого подтверждённого fill.
Трейлинг заменяет выход по fair; стоп и H остаются общими. Частичные fills не
сбрасывают экстремум. Старых полей вычета спреда, абсолютного допуска IOC и
порога выхода с обратным знаком в конфиге больше нет; старые конфиги нужно мигрировать.

`max_drawdown_usd = "30"` — остановка текущего запуска при падении
реализованного PnL на 30 USD от максимума: например, с +70 до +40.
Начальные PnL и максимум равны нулю; после перезапуска отсчёт начинается заново.
Удаление параметра отключает этот стоп; указанная сумма должна быть положительной.
Проверка выполняется только на новом fill, после дедупликации: берутся фактические
realized PnL и комиссия из уже получаемых WS/REST-сообщений. Открытый PnL в этот
максимум не входит. Пополнения, выводы, funding и чужие сделки не учитываются.
Новых запросов баланса и подключений нет. При срабатывании новые входы запрещены,
остаток закрывается reduce_only через штатное завершение процесса. Неизвестные
заявки не блокируют защитный выход. Стоп не снимается поздней прибылью или сигналом;
текущая закрывающая сделка может превысить лимит — это порог остановки, а не
гарантия точного ограничения убытка. Стоп позиции −5 bp и таймер не изменены.
В `/status` добавлены максимум, текущая просадка, лимит и факт срабатывания;
PnL стратегии теперь учитывает комиссии. В dry-run расчёт прежний, без комиссии.

```sh
cargo build --release --locked -p bb-bot
./target/release/bb-bot validate --config config/reference-arb-example.toml
./target/release/bb-bot run --config config/reference-arb-example.toml
```

`dry_run` — прежний параметр конфига; сейчас `false`, сеть `mainnet`: реальная торговля.
При `dry_run=true` ключ тоже требуется. Реальные заявки и отмены в dry-run не
отправляются, реальные fills не меняют виртуальную позицию. Симуляция
использует ликвидность видимого BBO в пределах IOC, без искусственного списания
всего допуска как проскальзывания. Её PnL не включает комиссии/задержку.

Для запуска используется release-сборка. Вывод логов выполняет стандартный
фоновый писатель `tracing-appender`: ожидание stdout/файла не задерживает
обработчики рынка. Форматирование строки остаётся в вызывающем потоке.
При переполнении очереди логи могут теряться; число потерь выводится при
завершении, торговля не блокируется. Guard писателя сохраняет хвост логов
при обычном завершении. Новых настроек логирования нет.

Неиспользуемые каналы Bullet закрыты; глубина и mark price для них больше
не преобразуются в события. Исходные данные глубины продолжают записываться.
Метка `received_at` ставится сразу после получения сообщения адаптером,
до подготовки записи и преобразования цен. У Bullet это момент выдачи
сообщения из SDK, поэтому ожидание во внутренней очереди SDK в неё не входит.

Убраны старые `order_size`, `max_position`, `persistence_ticks`,
`max_hold_ticks`, `reference_stale_secs`, `taker_fee_bps`, `min_edge_multiple`.
Вместо них — бюджет заявки, EMA, время удержания в секундах, свежесть Binance
`reference_stale_ms` (1000 мс), необязательная таблица импульса,
порог edge A, резерв лимита B и один выход: fair R или трейлинг D.
λ=1, биржевой шаг количества и задержка повторного входа 10 с не имеют
дополнительных настроек. A, R и I могут быть отрицательными;
проверяется конечность числа. B конечный и неотрицательный, D конечный и положительный.
Ограничения сетки B≤A и R≤A не добавляют запретов запуска. Нулевой допуск
выхода разрешён. Интервал таймера 0 отклоняется при загрузке конфига.
Отсутствие входных данных EMA/импульса означает отсутствие значения формулы,
а не отдельный флаг блокировки или дополнительный прогрев.

У Bullet BBO нет ограничения возраста; `exchange_stale_ms` удалён.
Пока в публичном пуле есть восстановленный стакан, последняя корректная
котировка используется для входов, EMA и сброса сигнала повторного входа.
Замена одного публичного WS и переподключение приватного WS её не сбрасывают.
После потери всех трёх стаканов нужен новый корректный BBO: старое сообщение
из очереди не снимает ожидание.
EMA сохраняется и после возобновления обновляется с учётом прошедшего времени.
Прошедшие 10 с повторного входа не разрешают вход до получения нового BBO.
Защитные выходы доступны по последним корректным ценам и во время ожидания.

Tick — внутреннее сообщение таймера. Интервал теперь 1000 мс: между
сообщениями проверяются H, повторы заявок и связь. Готовый ответ REST сразу
вызывает обработчик стратегии через штатный канал событий: учитываются fills
и проверяется выход, без ожидания тика или новой котировки.
Входы и ценовые выходы проверяются на каждой котировке, не ожидая тика.
В тишине проверка срока H может задержаться до секунды плюс задержка обработки;
статус логируется раз в 5 с.
Возраст котировки не запрещает закрытие. Сохранён исходный MARKET Bullet
через защищённый IOC: `market_slippage_bps=50` применяется только к выходу.
Частичный выход повторяется после подтверждения отмены остатка.

Небольшие изменения событий нужны для исполнения: у книги есть время
получения, у Binance отдельно mid и microprice, а приватные fill/status
Bullet передаются стратегии в одном упорядоченном потоке. Для сигнала
используется полный BBO, полученный из трёх независимо восстановленных
depth20. Общий book feed теперь содержит только готовые снимки принятого
стакана, а не смесь BBO и дельт. Приватные события и RPC используют отдельный WS.

Приватная подписка Bullet — `account@user.orders`: события этого аккаунта,
включая его ручные заявки и заявки другого процесса. Публичные `aggTrade`
попадают только в запись. ID ожидающей заявки проверяется один раз на входе
обработчика; поздний повтор старого ордера не завершает текущий. Это не
контроль общей позиции аккаунта при параллельной ручной торговле.
Запись каждой ожидающей заявки удаляется при её завершении;
причина выхода хранится только в `exit_requested`.
Цены Binance проверяет адаптер; повторной проверки цен и порядка его
локальных времён получения в стратегии нет.

При live-старте остаются штатная отмена заявок и проверка отсутствия начальной позиции.
Подтверждённый отказ освобождает ожидающую заявку; отклонённое закрытие
повторяется не чаще раза в секунду. REST нужен только для незавершённой заявки:
после неизвестного результата отправки, обнаруженного пропуска/ошибки разбора
fill, переподключения с ожидающей заявкой или отсутствия подтверждения дольше
секунды. Пропуск виден, если накопленный объём в событии превышает сумму
полученных fills. Переподключение в Flat/Holding не запускает сверку.
Обычная цепочка fill → cancel (включая пустой IOC) завершается по WS без REST:
отсутствие итогового объёма в cancel само по себе не означает потерю сообщений.

Неизвестная заявка блокирует новые входы, но не защитный `reduce_only` выход.
Стоп/gap/H отправляет защитное закрытие, не дожидаясь завершения входа или
предыдущего закрытия. Пока вход неизвестен, количество выхода — известная
позиция плюс ещё не подтверждённая часть исходной заявки входа. Это верхняя
граница возможной позиции; реально исполнимый объём ограничивает reduce-only.
Если закрытие не подтвердилось, его можно повторить
через прежний интервал 1 с. Все выходы направлены против исходной стороны
входа: биржевой reduce-only не позволяет повтору увеличить или перевернуть
позицию. Повторные запросы возможны; повторный учёт одного fill — нет.
Даже если fills входа пока не видны, gap/H и завершение бота могут отправить
такое закрытие. При полном отсутствии подтверждений входа H отсчитывается
от отправки; при известном исполнении — от первого fill. Стоп по PnL требует
фактической цены входа. Пустой выход при неизвестном входе повторяется не чаще
раза в секунду, чтобы не создавать цикл заявок на каждом cancel.
Запрошенное количество никогда само не записывается в позицию.

Существующая запись заявки теперь хранится для каждого незавершённого IOC.
Поздние fills сопоставляются с заявкой по client ID и учитываются один раз
по trade ID. Даже при временно нулевой позиции новый вход ждёт завершения
всех прошлых заявок. Поздний остаток входа закрывается с сохранением причины
выхода, basis_entry и первого времени исполнения. Запоздавшие сообщения
не меняют направление защитного закрытия на противоположное.

Отправка ордера выполняется в фоне; handle хранится в существующей записи заявки.
REST-сверка выполняется одной фоновой задачей, по очереди для ожидающих заявок.
Обе операции посылают `OrderTaskReady` через один штатный `MpscFeed`;
сетевые ожидания не удерживают обработчик стратегии. Котировки, fills и защитный
выход обрабатываются до ответа на отправку. Поздний ответ после WS/REST-завершения
заявки игнорируется; известный из приватного потока order ID не стирается пустым RPC-ответом.
При остановке, когда подписки уже выключены, результаты тех же задач ожидаются
напрямую вместе с таймером повторов.
Дополнительных настроек, HTTP-клиентов или менеджера задач нет.

Постановка, отмена, изменение и отмена всех заявок Bullet отправляются через
существующий `ManagedWebsocket` SDK. Брокер подписывает транзакцию штатным
`Transaction::builder`, передаёт команду в существующий muxer и получает
соответствующий RPC-ответ через oneshot. Единственная таблица в muxer сопоставляет
`request_id` с ожидающим вызовом; это не второй учёт ордеров или позиции.
Ожидание ответа одной заявки не задерживает отправку другой или обработку рынка.
Переподключение остаётся внутри SDK; при ошибке отправки SDK может повторить те же
подписанные байты с тем же nonce. Адаптер не пересоздаёт неопределённую заявку и
не пересылает её через REST. Исключение — один повтор после явного
`InvalidSignature` без разрыва соединения: обновляется schema SDK и подписывается отклонённая транзакция,
как в прежнем REST helper. `dropped` без причины остаётся неизвестным исходом,
поскольку это может быть ответ на дубликат уже выполненной транзакции.
Отказ на запрос, переживший разрыв соединения, тоже остаётся неизвестным:
он может относиться к повторной доставке, когда первая уже исполнилась.
RPC не меняет позицию: fills по-прежнему поступают только из приватного потока
или REST-сверки. Новых таймаутов и настроек транспорта нет; закрытие при завершении
использует прежний общий предел 10 с. REST остаётся для чтения состояния и истории.
REST может временно вернуть `Cancelled, filled=0` для уже исполненного выхода.
Пока локальная позиция ненулевая, такой выход сохраняется для следующих fills
и сверок; защитные reduce-only повторы доступны. Позиция и PnL восстанавливаются
только из фактических fills,
с прежней дедупликацией по trade ID; новых запросов или таймаутов нет.

Измерительный пример `order_latency` также принимает `ws-taker`: четыре
последовательных открытия BTC минимальным LOT_SIZE и четыре закрытия IOC.
Это реальные заявки mainnet через raw WS SDK, отдельно от стратегии/harness;
режим запускается только явной командой. Пример сохраняет локальное время
подписи/отправки/ответа, полные приватные fills и итоговую REST-историю.
Нормальный результат — восемь taker-исполнений и нулевая позиция.
Если пример возвращает ошибку, его журнал и фактическую позицию нужно проверить
до следующего запуска: он не повторяет неопределённые входы автоматически.

`reduceOnly=false` в REST-истории не отражает флаг отправленной обычной заявки.
В [официальной OpenAPI-схеме Bullet](https://github.com/bulletxyz/bullet-rust-sdk/blob/ca010466cb48c63d921e46ed2ec81cfb5a562855/rust/openapi.json#L5913)
поле `OrderHistoryEntry.reduceOnly` описано как фиксированное `false` для обычных
ордеров до появления `Event::PlaceOrderV1`. В сырых ответах `allOrders` и
`orderHistory` получено то же значение; SDK его не подменяет.

Проверка mainnet 2026-10-24 через SDK WS IOC подтвердила ограничение объёма:
long 0,0001 BTC + sell 0,0002 reduce-only → исполнено 0,0001, позиция ноль;
short 0,0001 BTC + buy 0,0002 reduce-only → тот же результат.
Биржа уменьшила объём ещё в сообщении NEW (`q=0.0001`), затем прислала FILLED.
Повторные sell/buy reduce-only при нулевой позиции отклонены с
`size_must_be_positive` (объём после ограничения — ноль), новых fills нет.
В подписанных вызовах сохранён `reduce_only=true`. Итог — четыре taker-fill,
PnL −0,0012 USDC, комиссии по API — ноль, BTC-позиция и открытые заявки — ноль.
Материалы: `data/runs/btc-reduce-only-20261024T174620Z.jsonl`,
`data/runs/btc-reduce-only-short-20261024T174805Z.jsonl` и
`data/runs/btc-reduce-only-verification-20261024T174948Z.jsonl`.
Временный тест использовал код существующего измерительного примера;
торговая логика, настройки и проверки бота не менялись.

В этом тесте REST-история сразу после fill ещё показывала EXPIRED с нулевым
исполнением, а `userTrades` был пуст. Последующее чтение подтвердило все fills
и FILLED; время появления истории отдельно не измерялось. Поэтому ранний ответ
истории не опровергает уже полученный WS-fill. Это отдельное наблюдение,
не причина фиксированного `reduceOnly=false`.

Отправка или завершение выхода не стирает вход и не отменяет его сверку.
Полный WS-fill или обычный cancel без признаков пропуска отменяет только
собственную ненужную сверку. Поздний ответ не переносится на другую заявку.

В локальном патче SDK 0.0.43 переполнение внутренней очереди учитывается
счётчиком потерянных сообщений. Адаптер проверяет его до обработки статуса
и включает сверку учёта. Уведомления о переподключении сохраняются в той же
очереди без потерь и в исходном порядке; потеря данных сама по себе не делает
однозначный отказ RPC неизвестным результатом. Отдельного WebSocket или
перехвата логов для этого нет.

Сверяются terminal-статус и сумма исполнений именно этой заявки; ожидание
совпадения с отдельно обновляющимся endpoint позиции убрано. Восстановленные
fills учитываются по trade ID, поэтому поздний WS-дубль не удваивает позицию.
Частичный вход не добирается; при выходе повторяется подтверждённый остаток.
Таймер H не продлевается новыми сигналами; для первого fill, найденного через REST, используется
время исполнения из истории. Повтор сверки — не чаще раза в секунду.
На всю сверку остаётся общий таймаут 5 с; отдельного таймаута 3 с на
каждый HTTP-запрос нет.

Запросы истории используют HTTP-клиент и пул соединений штатного SDK;
отдельного клиента нет. Небольшая обвязка пагинации остаётся: методы истории
в SDK 0.0.43 не принимают cursor. Open orders запрашиваются только при
неизвестном order ID. Пустой список открытых заявок не доказывает отмену.
Если старый защитный выход остался без RPC-ответа и отсутствует в истории,
сверка дополнительно читает `address_state` **подписывающего delegate** через SDK.
Точный `Window` nonce берётся из исходной подписанной заявки, сохранённой в
существующей таблице ожидающих RPC. Когда конец биржевого окна больше этого
nonce более чем на 1000, исходная транзакция уже не может исполниться.
1000 — размер окна протокола, а не таймаут в миллисекундах.
Только при полностью учтённом входе и нулевой позиции по fills старый выход
снимается с ожидания. Это исправляет зависание после потери первого выхода
и успешного закрытия следующим reduce_only. Новая заявка не подписывается
и не пересылается; статус отмены не выдумывается. При неизвестном входе,
ненулевой позиции или неподтверждённом сдвиге окна сверка продолжается,
защитные выходы разрешены. Дополнительное чтение выполняется в существующей
фоновой сверке; обычный IOC не вызывает его.
При штатном завершении до 10 с выполняется закрытие с подтверждением.
`ExecutionUpdate` доставляется обработчику напрямую из существующего mpsc-канала
адаптера (`sub_mpsc`), без промежуточной broadcast-очереди. После окончания
текущего обработчика harness передаёт этот же receiver актору для `wind_down`;
непрочитанные и вновь приходящие сообщения сохраняются. Перед расчётом
остатка для выхода обрабатываются уже полученные fills. Новые входы после
сигнала остановки запрещены, защитные reduce_only выходы остаются доступны.
Дедупликация и завершение частичного IOC используют обычный `apply_execution`.
REST остаётся резервом при разрыве/потере подтверждений; здоровый WS не требует
сверки каждого закрытия. Когда fills подтверждают flat и все заявки завершены,
остановка не ждёт обновления REST-индекса позиции. Cancel-all перед закрытием
не нужен: стратегия отправляет только IOC, остаток которых не остаётся в стакане.
Если flat не подтверждён к сроку, ошибка передаётся через harness в CLI после
выполнения очистки всех акторов; успешный выход процесса больше не маскирует её.
Новых параметров конфигурации нет. Полный BBO принимается и при
сбросе номера снимка со стороны Bullet.

Ограничение API: в истории закрытых ордеров нет гарантированного client ID.
Если потеряны ответ отправки и все WS-подтверждения, а IOC не дал ни одного
fill, без order ID исход может остаться неизвестным. Бот продолжит проверки,
но не отправит ещё один вход наугад. Восстановления сделки после аварийного
перезапуска процесса нет; перед новым live-запуском аккаунт должен быть flat.
`ArbState` удалён: статус вычисляется из позиции, ожидающих заявок и решения
закрыться. В dry_run только расчёт виртуального исполнения отличается от live:
fill и terminal-статус проходят общие `apply_execution`, `apply_trade` и
`complete_order`. Если при остановке доступного BBO не хватает для полного
закрытия, возвращается ошибка с остатком виртуальной позиции.
Подробные формулы и правила — в `crates/strategies/reference-arb/README.md`.

## Запись рыночных данных и исполнения

Запись включается секцией `[recording]` в том же конфиге `reference-arb`:

```toml
[recording]
output_dir = "data/market"
max_bytes = 20_000_000_000
```

Запуск — обычный `bb-bot run --config config/reference-arb-example.toml`.
Удаление секции отключает запись. Для остальных стратегий эта секция
вызывает предупреждение: бот запускается без записи, лишний писатель
не создаётся. Инструмент, сеть Bullet и рынок Binance
берутся из существующих настроек бота. Ключ требуется и для dry-run.
Отдельной команды `record`, подключений только для записи, таймаутов сборщика
и `duration_secs` нет. Запись завершается вместе с ботом.

Binance BBO объединяется из трёх подключений по общему номеру обновления `u`.
В запись попадает исходный текст первой корректной новой котировки; поздние
копии не записываются и не обновляют свежесть reference price. Публичный пул
Bullet также обслуживает и стратегию, и запись.
В запись поступает один итоговый поток полных depth20-снимков (`mt=s`, `pu=0`)
после объединения по T; отдельный `bookTicker` не подписывается и не пишется.
В снимке сохранены локальный `u`, исходные `E`/`T`, `connection`, `generation`,
`bbo_changed`, `bbo_forwarded`, `book_forwarded`. Восстанавливать цепочку по
`u` между снимками не нужно: эти номера принадлежат разным источникам.
Публичные aggTrade записываются по одному разу на trade ID, с источником;
они не поступают в Trade, отвечающий за изменение позиции.

В ту же очередь и файлы поступают приватные `ORDER_TRADE_UPDATE` (статусы
и fills), ответы торговых RPC `order.place`, `order.cancel`, `order.amend`,
`order.cancelAll` и ошибки RPC. Они записываются до маршрутизации и удаления
повторных fills: сохраняются повторы и поздние ответы, которых стратегия уже
не ждёт. Это позволяет сопоставить частичный fill, завершение IOC и попытки
`reduce_only`-закрытия по биржевым и локальным временам.

Для связи отказа RPC с заявкой сохраняется `rpc.request`: `id` запроса,
неподписанные параметры SDK `call` (включая `client_order_id`, размер, цену
и `reduce_only`), результат постановки в очередь SDK `queued` и ошибка
постановки `error`, если она была. Запись выполняется после попытки постановки,
чтобы сериализация не задерживала отправку. Её метки `recv_*` относятся к
этому моменту, а не к записи в сокет или исполнению на бирже. Ключ и
подписанная транзакция в `rpc.request` не сохраняются. `id` связывает запрос
с ответом внутри сессии; `client_order_id` связывает его с приватными событиями
и логом стратегии. Если SDK не разобрал входящий пакет, запись `unknown`
содержит ошибку разбора `error` и исходный текст `raw`.

Обычный лог независимо от рекордера сохраняет краткие параметры отправки,
RPC-ответы/отказы, приватные статусы и завершение учёта заявки. В сообщениях
стратегии об исполнении и ошибках указываются `client_id`, `order_id` и
`reduce_only`; у fill также есть `trade_id`. Поздние ответы сохраняются в логе,
даже когда ожидающий вызов уже завершён. Подписанная транзакция не выводится.
Так торговая история остаётся доступна при достижении квоты рекордера; обычный
лог тоже использует ограниченную неблокирующую очередь, поэтому абсолютной
гарантии сохранения при переполнении или отказе диска нет.

Строки начала, завершения и ошибки рекордера содержат тот же `session_id`,
что JSONL-файлы. `session_start.payload` содержит `recording` (настройки
хранения) и `run` (тип стратегии, её фактические параметры с применёнными
значениями по умолчанию и интервал тика). Настройки ключей туда не входят.
Периодический `arb tick` выводится на `DEBUG`. Явный отказ входного IOC с
причиной `IOC order received no fill`, если fills не было, выводится на
`INFO`; прочие отказы, включая отклонённые защитные выходы, остаются `WARN`.

В `payload` Binance сохраняется исходный текст победившей копии, без потери
полей `E`/`T`/`u` и неизвестных полей. Приватные сообщения Bullet
и RPC сериализуются из SDK; публичный depth — итоговый готовый снимок,
aggTrade — первая принятая копия с метаданными источника. Неизвестные SDK поля
и исходное форматирование не гарантируются.
Метки UTC/monotonic относятся к получению сообщения адаптером (после
разбора SDK у Bullet), а не сетевой картой. Указываются источник, тип
сообщения, сессия и порядок записи. События подключения и переподключения
приватного WS также сохраняются; жизненный цикл и рейтинг публичных WS
попадают в обычный лог. Метки объединённого depth и aggTrade сохраняют время
получения адаптером до восстановления/сериализации. Это не точный replay
порядка вызовов стратегии: feeds/harness могут пропускать котировки.
Флаги forwarded показывают постановку в канал адаптера, а не обработку актором.
RPC-подтверждение само по себе не является fill; время исполнения берётся из
приватного fill. Настройки записи и торговая обработка событий не меняются.

Формат — JSONL в последовательных полных zstd-фреймах. Ротация фиксирована:
около 64 МиБ на файл. Приблизительная квота по умолчанию — 20 000 000 000
байт. Перед открытием первого и каждого следующего файла суммируются размеры
обычных файлов непосредственно в каталоге записи; подкаталоги не обходятся.
Текущий файл дописывается до ротации, поэтому объём может превысить квоту
примерно на один файл. Это не строгая общая квота для нескольких процессов;
блокировки каталога нет.

При достижении квоты следующий файл не открывается. При квоте или ошибке
диска прекращается запись, бот продолжает работать; причина выводится в лог.
История не удаляется и не перезаписывается, автоматического перезапуска
писателя нет. Остаются проверка непустого output_dir, положительного
max_bytes и неизвестных полей конфигурации; настройки проверяются один раз
при загрузке конфига.

Ограниченная очередь записи не блокирует торговые подключения. При
переполнении записи пропускаются, счётчик потерь выводится в лог и поле
`dropped_total` следующих записей. Пишущий поток буферизует данные и
сбрасывает их по размеру или раз в секунду, в том числе когда новые сообщения
не поступают. Таймер, сжатие и файловый ввод-вывод обслуживаются тем же
выделенным писателем. При нормальном завершении писатель сам добавляет
`session_end` с итоговым `dropped_total` после принятых сообщений, затем
сбрасывает буфер и синхронизирует файл. Завершающая запись не конкурирует
за место в очереди. Это не обещание `fsync` каждую секунду: синхронизация
файла выполняется при ротации и штатном завершении. Полный бэктестер
не добавлен.

`log_lines_dropped` в обычном логе считает потери его очереди, а не ошибки
диска; используемый `tracing-appender` не включает ошибки вывода в этот
счётчик. Нулевое значение само по себе не подтверждает сохранность файла.

Для отдельной проверки сетевой задержки есть режим `ws-ping` в существующем
примере измерений:

```sh
cargo run -p bb-exchange-bullet --example order_latency -- ws-ping > ws-ping.jsonl
```

Он открывает восемь последовательных соединений через штатный
`connect_ws_managed`, подписывается на публичный BBO LIT и измеряет по десять
`ManagedWebsocket::ping`. Ключ не загружается, торговых запросов нет.
JSONL сохраняет времена отправки/получения, ответы и TCP-статистику собственного
процесса через Linux `ss`; соединение работающего бота не затрагивается.
Ping измеряет круговой путь запроса, а не исполнение ордера. При сравнении
публикации fill используются две биржевые метки `E` и `o.T`; разность локального
времени получения и `E` дополнительно зависит от расхождения часов.

В адаптере постоянно работают два приватных/RPC `ManagedWebsocket` SDK.
Оба подписаны на `account@user.orders` и mark price текущего инструмента.
Каждая новая торговая команда отправляется через один выбранный WS; общая
таблица RPC хранит исходный сокет и идентификатор запроса. Смена маршрута
не переносит и не повторяет уже принятые SDK команды. Повтор через второй WS
допускается только после `Busy`/`Stopped`: SDK явно не поставил команду в очередь.
Подписанная транзакция при этом та же. Ответ на неправильном сокете не снимает
ожидающий запрос; старые/поздние ответы сохраняются в записи.

На каждом сокете используются прежние ping-пробы: четыре измерения, первое
прогревочное, медиана остальных; следующая серия через 10 секунд. Новые команды
идут через канал с меньшей измеренной медианой, даже если оба быстрее 50 мс.
Первый таймаут ping (прежняя 1 секунда) переключает отправку на доступный
канал без таймаута, не дожидаясь конца серии и не закрывая старый сокет.
Просроченный pong не восстанавливает рейтинг. После восстановления ответа
скорость определяется новой законченной серией; прежняя медиана не используется.
При разрыве — через доступный канал, без ожидания ping. Если оба ping истекли,
сам таймаут не запрещает отправку защитной заявки через ещё подключённый WS.
Открытая позиция и неизвестный вход не запрещают смену маршрута отправки.
Задержка fill сама по себе не запускает ротацию: она включает работу биржи.

Для физической замены медленного WS переиспользуется существующий
`refresh_connection_if_idle`. Стратегия разрешает её после проверки входа/выхода
и только без незавершённых заявок; известная открытая позиция допустима.
Метод только ставит локальную команду в очередь и сразу возвращает управление:
oneshot-ответа от транспортного цикла больше нет. Его `bool` означает постановку
команды, а не завершение замены. Возможность замены забирается атомарно;
условия перепроверяются транспортом при обработке команды.
Адаптер дополнительно проверяет отсутствие ожидающих RPC на заменяемом сокете,
подтверждение подписки, наличие ping-замера и отсутствие таймаута у второго.
Заменяется худший маршрут с медианой выше 50 мс, не чаще раза в минуту.
Сначала закрывается старый WS,
затем SDK создаёт новый; третий приватный сокет для проб не открывается.
При сетевом разрыве реконнектом занимается SDK; после терминального отказа
пересоздаётся только потерянный слот. Подключение/пробы идут параллельно
другому рабочему WS. Перезапуск всего бота для этого не нужен.

Fills с двух каналов проходят общую дедупликацию по `trade_id`. Статусы могут
повторяться: более поздняя копия с непрерывного канала иногда подтверждает
полноту заявки, которую нельзя было подтвердить по первой копии нового канала.
`ExecutionUpdate.stream_started_at` передаёт время подтверждения непрерывной
подписки источника. Отдельная отмена без накопленного объёма завершает заявку
только на потоке, покрывающем её с момента отправки, и без известного пропуска.
Новый поток немедленно приносит fills, но не объявляет старый IOC пустым.
Частичный IOC `rs=0` с полностью учтённым накопленным объёмом завершается сразу,
в том числе через новое соединение, без REST.

Потеря одного канала при работающем втором не включает общую REST-сверку.
После потери обеих подписок используется существующее восстановление заявок.
Также сохраняется сверка при доказанном пропуске fills или ожидании исхода
заявки больше существующего интервала. Она не запрещает защитные reduce_only.
Публичные BBO, EMA и повторный вход не сбрасываются при смене приватного пути.

Неразобранный `ORDER_TRADE_UPDATE` также поднимает существующий флаг сверки до
передачи следующей отмены. Неизвестный служебный тип сам по себе этого не делает.
Потери внутри очереди SDK считаются отдельно от потерь записи: локальный патч
`bullet-rust-sdk` 0.0.43 в `vendor/bullet-rust-sdk` добавляет
`take_dropped_events()`. Адаптер проверяет счётчик после получения события и
до обработки статуса/RPC; положительное значение включает ту же сверку.
Потери данных не помечают RPC как неоднозначный: обычный подтверждённый отказ
освобождает заявку. `Reconnecting`/`Disconnected` сохраняются в той же очереди
без потерь и с исходным порядком благодаря гарантированному месту нового
`futures::mpsc::Sender` для редкого служебного события.

Готовность приватного маршрута берётся из фактического состояния SDK через
`is_connected()`/`connected_epoch()`. Восстановившийся сокет доступен сразу,
без ожидания чтения старой очереди. Вместо флага `interrupted` существующая
таблица RPC хранит номер соединения в момент отправки. Надёжные события
`Reconnecting` задают номер соединения для получаемых ответов (`received_epoch`);
отказ неоднозначен только если пришёл уже через более новое соединение.
Старый реконнект в очереди не портит результат новой заявки, а старые сообщения
не объявляют отключённый сокет рабочим. Флаги `online` в адаптере больше не
хранятся и не обновляются по сообщениям. Перед отправкой готовность проверяется
снова, и reduce_only сразу использует доступного соседа.
Уже принятый запрос не копируется на другой сокет; при реальном разрыве его
исход остаётся неоднозначным до подтверждения. Очередь данных, интервалы
реконнекта и протокол отправки SDK прежние; новых настроек или фоновых задач нет.
Нормальный IOC по-прежнему завершается без обязательного REST.

Приватные сообщения и RPC-ответы сначала передаются потребителям, затем
сериализуются существующим рекордером с исходным временем получения и полями
`connection`/`generation`. Приватные дубли сохраняются для разбора доставок;
учёт позиции от этого не повторяется. Подписанные транзакции и ключи не пишутся.
Сериализация напрямую читает поля сообщения SDK, без промежуточного дерева JSON.
Новых настроек TOML нет. Два приватных WS используют один SDK Client/ключ,
одного брокера и один учёт позиции; приватная подписка относится ко всему аккаунту.


## Три публичных WS Binance

`connect_binance` и `connect_binance_with_recording` используют один и тот же
пул из трёх `tokio-tungstenite` соединений для выбранного символа и рынка.
У Binance остаётся `bookTicker`: это полный BBO, поэтому снимок REST,
восстановление глубины и цепочка `pu` не нужны. Стратегия получает прежний
`ReferencePriceUpdate` с микропрайсом и арифметическим midpoint.

Первый корректный BBO с `u` выше принятого номера отправляется стратегии и
записывается один раз. Несколько разных `u` при одинаковом `T` не объединяются.
Поздние/повторные `u` не меняют EMA, историю импульса и время свежести.
Номер сохраняется даже после потери всех трёх соединений. После реконнекта
нужен действительно новый `u`; старый повтор не становится свежей котировкой.
Неверный символ или некорректный новый BBO не продвигает общий номер.

Правила рейтинга повторяют публичный пул Bullet: время приёма одинакового
`u` сравнивается с первой копией, считаются первые доставки, история ограничена
8192 идентификаторами. Первые 5 секунд каждого подключения исключены из оценки,
но его данные используются сразу. Раз в 5 минут от подключения последнего
из трёх каналов заменяется один худший. Сначала проверяется прекращение доставки:
если последние принятые данные канала отстают от последних данных соседей
на 5 секунд или больше, он выбирается раньше исторически медленного канала.
Используется уже собранная история и тот же пятисекундный запас, что у прогрева;
нового таймера или настройки нет. Общая тишина рынка не считается отказом,
возобновивший доставку канал снова оценивается наравне с остальными.
Далее выбор идёт по медиане опоздания; при недостатке
совпадающих сообщений используется вклад в первые доставки. При равном нулевом
вкладе молчащий канал уступает каналу, который доставляет измеренные копии.
Новые котировки не продлевают таймер. Переподключение запускает новое окно
рейтинга; пока подключается замена, два остальных продолжают работать.

Сначала старый сокет закрывается, затем открывается замена — четвёртого нет.
Сетевой разрыв восстанавливает только свой слот. Подключения идут отдельными
задачами с повтором 1→30 секунд и пределом 10 секунд на одну попытку соединения.
Ответы на серверный ping делает сам Tungstenite при чтении; обработчик не
ожидает отправку pong отдельно от чтения двух других сокетов.

Стратегия и рекордер получают данные без ожидания свободного места в очереди.
Если очередь стратегии заполнена, сохраняется только последняя непереданная
котировка. Освобождение места само пробуждает существующий цикл через
`Sender::reserve`: следующего рыночного сообщения ждать не нужно. Чтение трёх
сокетов продолжается и при полной очереди. Доставка сохраняет время первого
приёма и не дублирует запись. Новая котировка заменяет непереданную старую.
При закрытии потребителя завершаются все сокеты и незавершённые подключения.

Фильтр свежести Binance остаётся прежним — 1000 мс. Ротация не меняет состояние
Bullet и его приватных/RPC соединений, не вызывает сверку заявок и не запрещает
защитные выходы. Новых настроек и зависимостей нет. Каждый вызов подключения
обслуживает один символ; будущие активы могут иметь собственные независимые пулы.

## Три публичных WS Bullet

`market_data.rs` обслуживает один инструмент через три ManagedWebsocket SDK.
У каждого свой depth20: snapshot заменяет книгу, delta меняет уровни, нулевой
объём удаляет уровень. `pu` должен совпасть с предыдущим локальным `u`;
при разрыве цепочки или неразбираемых уровнях заменяется только этот WS.
Это необходимо в том числе потому, что сам SDK может пропустить сообщение
при переполнении своей очереди. Дельты применяются ДО глобального фильтра по T.

Готовые книги объединяются по `depth.T`: меньшая метка отбрасывается из общего
потока, равная метка с той же книгой — дубль. Конфликт книг при равной T
логируется, принятую книгу не заменяет. В стратегию отправляется только
изменение общего BBO; после потери всего пула повтор той же котировки также
снимает ожидание свежего снимка. Глобальная метка и дедупликация публичных
сделок переживают ротации. Приватный reconcile от публичных разрывов не включается.

Общий стакан публикуется и записывается один раз для каждого нового T. Если
очередь BBO была заполнена, сохраняется последняя непереданная котировка.
Освобождение места само пробуждает существующий select через `Sender::reserve`,
без ожидания следующего depth. Поздние копии не обновляют исходное время её
приёма, более новая BBO заменяет непереданную старую. При потере всех трёх стаканов
ожидающая котировка сбрасывается: для новых входов нужен свежий снимок.
Повтор доставки не повторяет запись стакана. То же относится к BBO с прежним T после
потери всего пула. Поля `bbo_forwarded` и `book_forwarded` в записи описывают
первую попытку доставки этого состояния. JSON снимка строится напрямую из
числовых уровней без промежуточного дерева JSON и отдельных строк цен;
прежний формат массивов строк сохранён. BBO отправляется до сериализации,
при заполненной очереди рекордера сериализация вообще не выполняется.

Таймер ротации отсчитывает 5 минут от готовности последнего из трёх стаканов:
при старте — от последнего первоначального снимка, после замены/разрыва —
от снимка восстановленного соединения. Обычные обновления таймер не продлевают;
пока хотя бы один стакан не восстановлен, плановая замена другого не запускается.
При срабатывании один раз рассчитываются и логируются медианы опоздания
относительно первой копии того же T и число первых BBO. Для медианы выбирается
средний элемент, полная сортировка не нужна. Измерения ограничены последними
8192 T в этом окне; первые 5 секунд после снимка не участвуют в рейтинге,
но данные используются сразу. Как у Binance, прежде медианы проверяется
прекращение доставки: канал без новых данных относительно соседей в течение
5 секунд выбирается первым. Проверка использует времена фактического приёма,
включая несовпадающие T; разные наборы T сами по себе не считаются пропусками.
Общая тишина рынка не штрафуется, возобновление доставки снимает этот приоритет.
Затем заменяется одно соединение с наибольшей медианой
опоздания; при равенстве — с меньшим вкладом в первые BBO. Если общих T не хватает
для сравнения всех трёх, выбирается соединение с наименьшим вкладом в первые BBO.
Новому снова даётся время накопить статистику; новое окно начинается после
восстановления всех стаканов. Дополнительного ожидания следующего пятиминутного
тика нет. При разрыве SDK сам переподключается; после терминального отказа
слот создаётся заново. Во время замены остальные два соединения работают.

Сначала закрывается старый публичный WS, затем открывается новый: целевое
число — три, во время замены может быть два. Плюс два приватных/RPC WS без дополнительного временного кандидата.
Новых параметров TOML нет. Пул привязан к одному symbol: расширение на другие
активы не вынуждает использовать общий рейтинг или одни и те же три маршрута.

Объединение опирается на сравнимость depth.T между источниками. Она проверена
на записи, но явная публичная гарантия полного порядка со стороны Bullet
не найдена. Конфликт равных T не скрывается. Запись полного стакана избегает
тройных копий, но размер файлов не обязан стать втрое меньше исходных дельт.
